# 麦懂你

先确认本次餐段、预算、门店和用户主动表达的组成习惯。可以把"两只汉堡，不买饮料"记录为 `burger: min=2,max=2` 与 `drink: max=0`。把"不爱喝可乐"和"不购买任何饮料"区分开；只按用户表述保存。用户没说喜欢鸡肉或牛肉，就不要替他推断。

## 获取真实候选

使用已配置的麦当劳 MCP，或运行仓库根目录 `python habit.py mcp-tools` 查看服务实际提供的工具与 `inputSchema`。不要猜测门店编号、餐品编码、优惠券条件和参数名。

1. 用 `now-time-info` 确认时间；用 `query-nearby-stores` 查询用户给出的附近位置。用户明确选定门店后继续，避免把不同门店菜单混合。
2. 用 `query-meals` 获取当前餐段菜单并保存原始响应到 `private/`。按需用 `query-meal-detail` 展开套餐组成，核实每一个组成项及可替换项；饮料可换水也仍是饮料，不要从商品名称猜测。
3. 在用户需要使用账户券时调用 `query-store-coupons` 或 `query-my-coupons`。不要默认两张券可叠加，也不要用菜单标价相加替代含优惠的最终试算。
4. 用 `plan` 完成枚举与计价。它会按 `category_limits` 枚举合法组合（同款多份、类别上下限），对每个候选单独调用 `calculate-price`，再排序：

```bash
python habit.py plan --profile private/profile.json \
  --menu private/menu-response.json --mapping private/mapping.json \
  --meal lunch --budget 30 --store <门店编号> --checked-avoid <已核实忌口>
```

`--prices <回放文件>` 可替换实时计价，用于无 Token 时验证链路。`--out` 保存规范化候选供复查。`--max-quotes` 控制一次最多试算多少个组合（默认 40），用于守住调用额度；输出会写明跳过了多少个、多少个计价失败，复述结论时不要省掉这两个数字。

枚举上限为每类别最便宜 6 个餐品的组合，因此结果只代表"已收集候选"内的最优，不能宣称全菜单最优。

## 字段映射

`--mapping` 指向一份显式路径映射，不是官方接口定义。字段名按实际响应填写，规则见 `MCP_INTEGRATION.md` 第 4 节：`*` 展开数组，`price_unit` 必须声明 `yuan` 或 `cents`，`${...}` 是计价请求模板。映射对不上会直接报错——**不要为了让命令通过而伪造字段或放宽单位**。

映射成功后用 `recommend --catalog <规范化的 private 文件>` 复核排序，或直接读 `plan` 输出。

## 档案与决策

用户明确要求的餐品数量、预算、忌口先过滤，再比较明确口味与历史反馈。对新用户，没有口味记录时按价格排序，不用人口属性或饮食标签臆测偏好。资料不足时说明还不知道什么。

`checked_avoid_tags` 表示已经核实的忌口检查范围。用户有忌口但信息缺失时，候选不得进入推荐；`plan` 在档案含忌口却没有 `--checked-avoid` 时会直接拒绝运行，这是预期行为，不要绕过。该标记由使用者依据可靠餐品信息填写，脚本不做食材或过敏原识别；过敏原信息缺失时告知无法确认。

输出最多三种不同候选：最合口味、预算优先、换个口味。标签按证据降级：没有候选命中口味标签时不会出现"最合口味"，而会显示"预算内可选"或"价格优先"。清楚说明每份组合、总价、匹配原因、未满足条件和比较范围。没有合格候选时如实报告，不偷偷放宽忌口和"不买饮料"。

用户对吃过的餐品明确点赞或不喜欢后，才执行 `feedback --profile <私有档案> --meal lunch --tags chicken,non_spicy --rating like`。使用经核实的口味标签；不要把刚推荐的餐品当作用户吃过，也不要把一次选择变成永久禁忌。档案可编辑或删除。

## 验证边界

`demo` 与 `examples/replay/` 都是虚构数据，不能作为真实 MCP 调用证明。无 Token、网络失败、试算失败时报告具体缺失，不伪造真实响应。本 Skill 仅查询与试算，不调用领券、下单、取消、积分消费等工具；客户端白名单会拒绝写操作。
