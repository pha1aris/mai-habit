# 麦懂你（mai-habit）智能体指令规范

在执行推荐前，优先明确本次用餐的时段、预算上限、目标门店及用户主动声明的结构性吃法。例如将“两只汉堡、不配饮料”规范化录入为 `burger: min=2, max=2` 与 `drink: max=0`。严格区分“不爱喝某种具体饮品”与“完全不购买任何饮品”的语义差异；仅依用户明确表述建档，未明示偏好时切勿主观臆测。

## 先建档，再推荐

**用户未明确用餐习惯前，切勿盲目执行 `plan`。** 仓库内置的 `examples/profile.json` 仅是通用展示示例，并不代表当前用户的真实需求；若直接套用示例运行，无异于替用户擅自拟定偏好。

建档前请核实四项核心信息（缺失项按需向用户确认）：**就餐餐段、组成习惯（主食份数、饮品需求）、单餐预算、明确声明的口味或食材忌口**。确认后通过命令初始化档案：

```bash
python habit.py init --burger 2 --drink none --budget 25 --tags chicken,non_spicy --avoid peanut
```

在对话交互场景中，亦可在终端执行无参数的 `python habit.py init` 启动交互式引导，或直接将用户的口述需求提炼为上述命令行参数。

用户档案中的 `source` 属性必须为 `user`。若执行输出中出现「示例档案」警示，表明当前正套用公共示例，应立即暂停并向用户确认习惯，不可将示例结论当作个性化输出。由 `init` 保存的预算将作为默认值，后续执行时 `--budget` 可缺省；仅在临时变更预算时显式传入。

## 获取与处理真实候选池

接入已配置的麦当劳 MCP 服务，或在项目根目录运行 `python habit.py mcp-tools` 查看服务端实际开放的工具列表与 `inputSchema` 规范。严禁在代码中臆测门店编号、餐品编码、优惠券规则或参数结构。

1. 调用 `now-time-info` 校验服务端时间；调用 `query-nearby-stores` 检索用户所在位置周边的有效门店。待用户明确指定目标门店后再行推进，避免不同门店的库存与价格交叉污染。
2. 调用 `query-meals` 获取当前餐段在售菜单并将原始响应妥善保存至 `private/`。遇到组合餐品时按需调用 `query-meal-detail` 展开详细构成，逐一核验所有组成项及可替换规格（例如：饮品支持换水仍属于饮品类目，切勿单凭商品名称主观臆断）。
3. 当用户需要抵扣卡券时，调用 `query-store-coupons` 或 `query-my-coupons`。切勿默认多张优惠券可无条件叠加，亦严禁以菜单标价机械累加替代含优惠的券后试算。
4. 运行 `plan` 子命令完成组合枚举与精确计价。系统将依据 `category_limits` 枚举合规组合（支持同品多份、分类数量上下限剪枝），对每个候选组合单独发起 `calculate-price`，随后综合排序：

```bash
python habit.py plan --profile private/profile.json \
  --menu private/menu-response.json --mapping private/mapping.json \
  --meal lunch --budget 30 --store <门店编号> --checked-avoid <已核实忌口>
```

- `--prices <回放文件>`：使用本地脱敏样本替换网络实时计价，用于零 Token 验证全链路逻辑；
- `--out <输出路径>`：将规范化候选集落盘，便于调试与人工复核；
- `--max-quotes`：约束单次试算的最大组合量（默认 40），用于严格管控下游 API 调用配额。输出中会明确标注入选试算数与跳过数量，智能体在复述结论时须如实保留该指标。

> 枚举池默认选取各品类单价最低的前 6 款餐品进行组合计算，因此推荐结果代表“当前成功枚举候选池”内的最优解，切勿虚假宣称为全门店全局最优。

## 声明式字段映射规范

`--mapping` 指向一份显式的 JSON 路径映射配置，并非硬编码的官方接口契约。字段规则须依据实际抓取到的响应进行配置（详见 `MCP_INTEGRATION.md` 第 4 节）：支持 `*` 展开多层数组，`price_unit` 必须显式声明 `yuan` 或 `cents`，`${...}` 用于定义计价参数请求模板。当映射配置与实际响应不符时系统将立即快速失败报错——**严禁为迎合命令通过而伪造映射字段或篡改金额单位**。

完成映射适配后，可运行 `recommend --catalog <私有规范化文件>` 单独复核打分模型，或直接读取 `plan` 的完整决策报告。

## 决策画像与反馈学习

系统优先依据餐品数量习惯、单餐预算及食材忌口进行硬过滤，再结合明确口味与历史反馈进行软打分。对于新用户，在缺乏偏好沉淀时严格退化为按价格排序，严禁基于通用人群标签主观猜测偏好；信息不完备时客观陈述未知项。

`checked_avoid_tags` 代表经人工或可信源确认的忌口原料排查范围。若用户画像包含忌口要求但未提供已核实的排查清单，该候选绝不可进入推荐池；当档案含有忌口而调用未携带 `--checked-avoid` 时，`plan` 将直接拒绝执行。此为核心安全预期行为，切勿绕过。脚本本身不具备生鲜食材过敏原的医学识别能力，相关原料信息缺失时应明确告知用户无法核验。

推荐结果最多输出三种梯队方案：**最合口味、预算优先、换个口味**。标签根据证据充分性自动降级：无候选命中口味偏好时，绝不展示虚高的「最合口味」，而是客观降级标注为「预算内可选」或「价格优先」。全面披露每份组合的明细构成、应付总价、匹配分值、未满足条件及对比基准；无合规候选时据实告知差额，严禁暗中妥协忌口约束或私自补加饮品。同时具备商业级“超预算最优加钱升级”（Upsell / Stretch）机制：全额超标时精准提示距离吃饱差额最少的底线方案；预算充足时，智能推荐合理零钱区间（如 +¥0.50）内的高品质/纯偏好升级组合。

当用户对实际就餐的餐品明确表达好评或不满后，方可执行反馈录入：`feedback --profile <私有档案> --meal lunch --tags chicken,non_spicy --rating like`。反馈须采用经确认的口味标签；严禁将系统刚推荐过的方案假定为用户已就餐，亦不可将单次负向反馈演化为全局永久屏蔽。本地档案支持随时查看与编辑修正。

## 安全与验证边界

`demo` 模式与 `examples/replay/` 目录均系虚构样本，不可作为真实 MCP 联调合格的证据。在无 Token、网络抖动或计价失败等异常场景下，智能体应如实报告缺失原因，严禁捏造虚假调用数据。本 Skill 仅获授权执行只读查询与试算操作，坚决不调用任何领券、下单、取消、积分兑换等写操作接口；客户端白名单在代码层强行拦截违规请求。
